# Kestrel: review the design, not the code

2026-10-28. Task WA-925. Status: skeleton reviewed 10-28 (William: A, C, D, E, F yes; B changed). Step 1 built locally (imports, diff, store, approve, check). Never in a lint or test gate (William, 10-28).

## Goal

William owns the design of every repo without reading code: organization, design patterns and
interfaces, not syntax. He reviews five layers, each made from the code, so none can drift:

| Layer | Question it answers | Made by |
|---|---|---|
| imports | which file and package uses which | dependency-cruiser (API, not the bin) |
| api | what each package gives out: functions, types and shapes, with signatures | ts-morph over source |
| routes | what can be called from outside a process: Restate handlers, HTTP routes, with input and output types | ts-morph over the registration calls |
| schema | migrations, tables, columns, keys, indexes | tbls on a migrated Postgres |
| systems | repos, units (Workers, Lambdas, containers, stores) and the links between them | deploy files and code facts, plus a residue in kestrel.json |

The ICM cards stay. They hold what code cannot say: why this shape, trade-offs, extension points,
what a change hits. A new card type, `pattern`, holds one design pattern (cursor pagination, the
send verdicts) and covers every node that uses it.

Every node has a `role` (repo, system, service, route, package, file, export, migration, schema,
table, index, screen) and a `parent`. Role gives the high-level view ("here are the migrations,
the DB, the backend, the screens"); parent gives the zoom from a repo down to one index. Kestrel checks that cards and generated files agree. Devboard shows copies to
annotate; it is never the source.

## The flow it serves

1. Discuss.
2. Design packet: this doc's shape, per change.
3. William annotates (Devboard copy).
4. Skeleton: real files, types, signatures, `todo()` bodies. It must typecheck.
5. `kestrel gen` on the skeleton. William reviews the generated pages. `kestrel approve` + commit.
6. Bodies.
7. `kestrel check` when a design step ends (skeleton approved, bodies done, a design review): drift
   from approved shows. Never in lint or tests: those stay fast.
8. Ship.

Kestrel itself went through 1 to 5. Steps 3 and 5 are one pause here: William saw the tree in chat.

## Patterns

- Adapter: each tool sits behind `Layer`. diff, store and cards know only `Graph`.
- One data shape (`Graph`): every later feature (site, packet, a new layer) works on all layers
  at once.
- Approval as a commit: `approved.json` changes only through `kestrel approve`. The commit's diff
  is the review record. No database, no server.
- Groups: a package, a table, a service. Storage only: one file per group keeps each git diff
  small. William approves the whole map at once, never per unit.

## Files in each repo that uses it

```
kestrel.json
map/generated/<layer>/<group>.current.json    every gen; check compares it; gitignored
map/generated/<layer>/<group>.approved.json   kestrel approve only
map/generated/<layer>/<group>.md              Mermaid page to read
map/objects/...                               ICM cards; frontmatter adds covers + stamp
```

Card frontmatter, new keys:

```yaml
covers: ["imports:@wren/outreach", "schema:table:reach_posts"]
stamp: 3f9c1a2e   # hash of the covered approved nodes when a person last read the card
```

A card is stale when its covered nodes change and nobody restamps it. That replaces the hand
`verified: date @ commit` with a check.

Only `approved.json` and `.md` are committed (wren: 8.7 MB → 4.4 MB). A repo also skips
`map/generated` in its linter and in any guard that reads exports by name (wren:
`biome.json`, `scripts/exports-guard.mjs`): the JSON names every export but reads none.

## Trade-offs

- One shared Graph shape drops tool detail. Detail that matters goes in `attrs`, compared exactly
  (index columns and uniqueness, a signature's text).
- Signatures compared as text: a rename of a parameter shows as drift. Accepted: a public
  signature change should be seen.
- tbls needs a live, migrated Postgres. The layer starts its own (testcontainers, as wren's
  tests do), runs the repo's migrate command, reads it, and stops it: 11 s on wren. Docker must
  run. `KESTREL_DB_URL` reads a database already migrated (CI) instead.
- dependency-cruiser's bin refuses Node 25 (this Mac). Its API runs fine, and kestrel uses the
  API anyway.
- API Extractor dropped: it reads built `.d.ts`, and wren never emits. ts-morph reads source.
- File-level imports are big: wren gives 2,220 nodes and 11,146 edges (2.6 MB in 44 files). Stored
  per package, so each git diff stays small.
- `check` on wren takes 11 s and 2.3 GB of memory (dependency-cruiser runs the TypeScript compiler).
  So it is a design tool, not a gate: lint and tests stay fast. Cost: nothing forces the map to stay
  approved between design steps; drift collects until the next check. Run it under the checks lock.
- Workspace packages resolve through their `exports` map (`enhancedResolveOptions.exportsFields`).
  Without it, every `@wren/*` import looks like an outside package.
- LikeC4 over Structurizr: TypeScript, npm, static site; no Java or Docker.

- api on wren: 9,283 exports, 4.8 MB, 48 s, 2.1 GB. One node per declaration a package gives out;
  its entries are a list. Comments are cut from every signature (cards hold the why).
- Where the code declares no type, the checker's text is cut to 300 characters and the node is
  marked `inferred`. Drizzle and zod types otherwise run to 30 kB each. 2,631 of wren's exports
  (28%) are inferred: a weak interface, listed by the health report (step 7).
- routes on wren: 61 services, 222 handlers, 15 s. Input and output come from the handler's type
  annotations. A name given at run time (`o.name`) shows as its source text. A name used twice
  shows as two services (`Executor` in `core/src/testing.ts`).

## Extension points

- New layer: one file in `layers/`, one entry in `LAYERS` and `LAYER_IDS`, one config block.
  routes reads Restate's registration shape; another framework (Hono, Express) is one more
  reader in the same file.
  Next likely: Python imports (import-linter) for keycycle; Restate services from discovery.
- New check: a function over `Graph[]`, called from `check`. Example: a layer rule like
  "packages/core imports no channel-*".
- `site` (one index over all repos): reads the store, later.

## Systems from code (step 10)

10-28, William: "why is the system map by hand? it should be deterministic based on the code."
The proof: the hand model listed no autobrowse → credvault link, though autobrowse's package.json
names credvault 0.13.0. It also missed listmonk, documenso, PgBouncer, the share and pixel Workers.
`kestrel check` only confirmed that its paths existed.

| Option | Good | Bad |
|---|---|---|
| A. Keep the hand model; a check compares it with package deps | Small | Finds only npm links. Every other miss stays |
| B. Generate the systems graph from deploy files and code facts, a residue in kestrel.json | A missed link is drift by construction | Readers to write and keep: wrangler, Terraform, containers |
| C. Generate a `.c4` file, keep LikeC4 | Same as B, plus LikeC4 tools | Nothing else reads the `.c4`: a format to keep for no reader |

Ranked: correct by construction first, then the fewest hand facts, then build cost. Pick B.
LikeC4 goes.

How it reads:

- **Units** (role `part`) come from deploy files: each `wrangler.toml` (a Worker, its bindings to
  D1, KV, R2, Durable Objects and services), Terraform `.tf` (Lambda functions, buckets, the
  instance, CloudFront), containers (`docker run --name` in scripts, compose services) and systemd
  units. Each is placed on its host.
- **A unit's bundle** is every file the imports graph reaches from its entry. A fact found in a
  file belongs to each unit that bundles it: an env var it reads (to a target from the residue),
  an SDK it imports (to a vendor), a Restate service it registers. The file is the edge's `here`.
- **Repos** (role `system`): the subject repo and the sibling repos the residue names. A package
  dep between two of them is an edge.
- **The residue**, `layers.systems` in kestrel.json: what code cannot say. Sibling repos, the
  target of each URL env var, the vendor of each SDK, a unit's entry when the deploy file does not
  name it (a Lambda's zip), the host of a script.
- **One-liners**: the unit's package.json `description`, else the deploy file's header comment, else
  the residue. None is a health signal, not a check failure.

William's bar: speed. Information is quick to reach and easy to read, with depth one click away.

How it stays fast (overview first, zoom and filter, details on demand):
- Layout computed at gen time: opening runs no layout.
- 7–12 boxes per level; children fold into their parent. systems → packages → files → exports, routes.
- Pre-attentive cues: color = role, size = fan-in, outline = drift since approve, badge = no card or stale.
- One click: signature, routes, indexes, the card's why, patterns, cost.
- Keys: `/` search, arrows move, `n` note to the session (Devboard inbox).
- Looks from the design-language artifact.

As built (10-28, on wren: 2016 files, 9276 exports, 222 routes, 177 levels):
- Tree: repo → `apps/` `packages/` → package → folder (`src/` dropped) → file. Exports and routes
  are rows in the file's panel, not boxes. A folder's panel lists its services, one line each.
- Each import edge sits on one level: the one where its two ends part.
- ELK layered, left to right: boxes are wide and short, so stacking them down a layer fits the

  The flat folder is itself a finding for the health report (step 7).

- Layout cache: `node_modules/.cache/kestrel/view.json`, keyed by each level's input plus

- Imports exclude `build/`, `coverage/`, `storybook-static/` (bundled assets read as 140 files).
